# 自动化推理的项目主线

梳理日期：2026-09-30。依据为本地源码、数据契约、设计图和项目说明。目录中的日期反映项目组织顺序；只有 SDL 与 Mentor 的演进具有原始 Git 提交可供核验。

## 1. 总体目标与技术分工

各项目共同尝试把输入资料转成机器可操作的表示，由模型或算法提出候选，再通过确定性检查、运行测试或统计确证决定是否接受，最后留下可追溯记录。

| 层次 | 采用的技术 | 对应项目 | 所产生的结果 |
| --- | --- | --- | --- |
| 资料获取与解析 | Docling、OCR、n8n、Markdown、结构保护 | n8n-Docling、CLC、CRD、架构工作台 | 来源文本、章节、表格、引用位置 |
| 知识表示 | JSON Schema、知识节点、层级约束、有类型关系、图谱 | CLC、CRD、Wiki | 有出处的概念集合、目录和关系图 |
| 计算表示与调度 | IR、DAG、寄存器与内存依赖、仿射访问分析、CPU/GPU/NPU | PLDA | 并行可行性报告、执行计划、计算结果 |
| 经验规律发现 | AST 表示构造、模式搜索、竞争假说、筛选、冻结与检验 | SDL M2–M6 | 候选表达式、假说、确证报告 |
| 推理控制 | 角色令牌、证据分区、工具目录、LLM function calling、AST 受限执行 | SDL M1、M10–M12 | 受约束的工具调用和分析结果 |
| 自动改进 | 多角色智能体、限定文件范围、测试、独立审查、补丁 | Self Renew | 验收需求、候选代码、交付报告 |
| 应用构建 | Teacher/Student、AppSpec、确定性工作流编译、证据与业务规则 | Mentor | 工作流应用规格与部分运行实现 |
| 展示与复核 | 原生 draw.io XML、图谱 UI、MediaWiki、Obsidian、Anki | 架构工作台、CRD、Wiki、学习工具 | 可编辑图、可读知识与复核入口 |

这里的“推理”包含知识关系判断、程序依赖判断和统计假说确证等不同任务。模型提出的解释、引用存在、结构检查通过、统计结果与代码测试通过，各自证明的内容不同，不能互相替代。

## 2. 知识输入主线

**原始资料 → 解析 → 分块提取 → 结构化概念 → 校验 → 阅读与复核。**

- `n8n-Docling` 已实现文档解析、翻译、复核、重点排版与 Obsidian 章节写入；保护代码、公式、图片标记。它是资料处理工具，翻译复核不会产生数学证明。
- `ConceptLayerConstructor`（CLC）用模型提取知识点，再规划层级。`clc/models.py` 定义数据契约，`clc/build.py` 负责构建、去重和图校验，`clc/parse.py` 校验引用，`clc/store.py` 与 Worker 管理 SQLite 任务。
- `ConceptRelationDraw`（CRD）从文档提取概念，结合全文分析关系，保留依据和人工复核；`grounding.py` 检查概念与关系引用，`pipeline.py` 管理阶段，`layout.py` 与前端呈现关系图。
- Wiki、Obsidian 和 Anki承载阅读、展示与学习操作。Wiki 的形式系统、逻辑与数学资料是知识内容，不是已实现的定理证明器。

CLC 着重目录与独立知识点，CRD 着重概念间关系。二者目前各自接收资料，各有数据契约；源码中没有把 CLC `graph.json` 直接接入 CRD 或 SDL 的共同适配层。

## 3. 计算执行主线

**明确契约的输入 → 统一 IR → 依赖判断 → 并行计划 → 设备调度 → 结果提交。**

`TheStructure.drawio` 描述 DEVICE、通信基础设施与数据处理模块。PLDA 在通信与执行基础设施中承担并行分析和调度：

1. `plda/model.py`、`plda/io.py` 管理 Program、Task、Tensor 与输入契约。
2. `plda/analysis.py` 分析 ILP/TLP/SIMD；寄存器和内存依赖用于保守判断，未知情形明确报告。
3. `plda/planner.py`、`plda/runtime.py` 按 DAG、关键路径、设备槽位、内存和搬运成本派发任务。
4. `plda/backends.py`、`plda/kernels.py` 提供受支持的 CPU、CUDA/OpenVINO 内核，失败与取消由运行时处理。

PLDA 判断有限 IR 的依赖与可执行性。它的“逻辑判断”具有程序契约边界，不是任意自然语言推理；ILP/SIMD 分析也不是机器码生成器。硬件加速的实际可用性取决于设备与厂商运行时。

早期 `OG-01-Servomechanism` 的信号量接口及两组 PRT 的 POSIX 文件操作练习，属于系统机制准备；未发现它们已经与 PLDA 或 SDL 形成可运行调用链。

## 4. SDL：目前最完整的发现与确证闭环

**观测语义登记 → 探索与开发 → 候选假说 → 冻结计划 → 独立确证 → 主动取数与归档 → 下一轮。**

| 模块 | 代码入口 | 职责 |
| --- | --- | --- |
| M1 | `sdl_m01/service.py`、`store.py` | 原始快照、E/V/C 分区、角色访问、冻结绑定与审计 |
| M2 | `sdl_m02/expressions.py`、`represent.py`、`domain.py` | 候选表达式与定义域、量纲表示 |
| M3 | `sdl_m03/equations.py`、`stability.py`、`structure.py` | 关系、稳定性及结构模式搜索 |
| M4 | `sdl_m04/generate.py`、`hypothesis.py` | 可检验解释与竞争假说 |
| M5 | `sdl_m05/metrics.py`、`select.py` | 开发评估与筛选 |
| M6 | `sdl_m06/freeze.py`、`execute.py`、`report.py` | 冻结计划、确证执行与报告 |
| M7 | `sdl_m07/acquisition.py` | 提出下一轮取证建议 |
| M8 | `sdl_m08/archive.py` | 结果与知识历史归档 |
| M9 | `sdl_m09/collection.py` | 驱动数据源取数并交 M1 登记 |
| M10 | `sdl_m10/toolbox.py` | 将算法原语封装为工具目录与调用护栏 |
| M11 | `sdl_m11/driver.py` | 连接模型、生成工具 schema、循环工具调用与结果回喂 |
| M12 | `sdl_m12/sandbox.py` | 对模型代码作 AST 检查、受限执行与资源限制 |
| 编排 | `sdl_pipeline/loop.py` | 发现、确证、取证和归档循环 |

M10 提供工具，M11 才执行真实的模型交互；M7 给建议，M9 执行取数。算法校验和确证步骤约束模型输出，模型不能自行授予证据等级。原始协议、确证用途和后续历史学习必须保持区别。

现有 SDL README 主要描述 M1，不能用它来判断整个工作目录的实现范围。`INTERFACES.md`、M2–M12 源码及相应测试是后续功能的入口。当前 `pyproject.toml` 只打包 `sdl_m01*`；完整模块使用须从项目目录运行，安装后的完整 SDK 打包尚需后续调整。

## 5. Self Renew：自动研发闭环

**读取项目 → 审计与创新分析 → 有验收条件的需求 → 隔离开发 → 测试与独立审查 → 集成补丁 → 再分析。**

`renew/repository.py` 创建项目快照，`renew/prompts.py` 与 `schemas.py` 定义角色和结构输出，`renew/runtime.py` 接入 Codex CLI 或 Responses API，`renew/pipeline.py` 管理开发、审查、依赖与停止条件，`renew/report.py` 产生交付记录。

候选修改限定文件范围。引用核对保证分析关联到真实代码；配置的测试和独立审查决定交付状态。离线演示使用固定模型脚本；它验证流程，不证明真实模型能发现所有缺陷。该程序可以用于改进其他子项目，但本次整合没有自动启动付费模型研发循环。

## 6. Mentor：把推理流程编译为应用

**需求与样本 → Teacher 设计 AppSpec → 确定性编译 → Student 运行 → 证据与规则校验 → 人工修订与离线改进。**

原始 3 个 Git 提交仅包含设计文档和许可证；工作目录另有未提交的 `pyproject.toml`、`uv.lock` 及 `src/mentor/`。此次一并纳入这些实现文件。

已发现的代码包括领域类型、配置、数据库、存储、文档处理、模型适配器、规则、工作流编译与运行时。`runtime.py` 已包含登记、任务领取、执行、提交、取消和复核方法。尚未发现 `mentor/api.py`、`cli.py`、Worker 入口或测试目录；`pyproject.toml` 中 `mentor.cli:app` 入口因此还不可用。Teacher/Student 的完整设计、发布门禁、性能指标和端到端能力不能按 README 视为已交付。

## 7. 架构工作台：让推理过程可检查

`ThePicWorkingFlow` 读取代码与文档，记录路径、行号、内容散列和 Python AST 符号，经分析模型与设计模型得到受约束 JSON，再确定性渲染 draw.io，校验页面、模块、包含关系、边端点、颜色及布局。`observed` 节点必须带真实来源；`proposed` 表示建议。

这条主线使复杂系统的结构解释可以定位到证据，并以图形复核；图的结构正确仍不等于架构语义解释完全正确。

## 8. 后续整合的具体接口

本次已经完成仓库、历史和文档整合。下面是根据当前代码提出的下一步技术连接，尚未实现：

1. **知识输入适配**：将 CLC/CRD 的来源、概念、关系映射为 SDL 的观测语义及探索输入；保留引用与转换版本，不能把模型解释当作独立确证证据。
2. **计算适配**：把 SDL 中符合 PLDA 纯内核契约的计算转换为 Program/Task/Tensor；保留严格或宽松浮点语义、设备依赖与失败状态。SDL 的角色令牌和确证访问不下放给计算后端。
3. **工具登记**：在既有 M10 工具护栏上增加显式适配器，使 M11 调用资料和计算能力；保持有限预算与受限结果句柄。
4. **工作流产品化**：补齐 Mentor 的 API/CLI/Worker 和测试，以 AppSpec 包装已验证的文档能力；Teacher 设计、Student 执行以及发布门禁各自留下版本记录。
5. **研发反馈**：让 Self Renew 分析具体子项目并交付可审查补丁；通过测试与人工验收后再合入主线。

共同的数据桥建议包含 `source_id`、内容散列、来源位置、表示版本、任务 ID、参数、执行记录与结果状态。实现时以现有各模块契约为准，不能仅通过改名把异构 JSON 声称为统一协议。
